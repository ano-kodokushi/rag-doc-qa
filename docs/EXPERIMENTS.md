# 对照实验记录（EXPERIMENTS）

本文件存放**受控对照实验**的设计、原始数据与结论。
每条实验都必须写明：受控条件、自变量、**方法学限制**、以及结论是「方向性证据」还是「统计显著」。

**为什么单独建这个文件**：项目的评测数字（`eval/report.json`）只说"现在是多少"，
而对照实验回答的是"**改动到底有没有用**"。这两件事必须分开存放，否则很容易把波动当成进步。

## E-01 · multi-hop 的瓶颈在检索还是生成？（T-016，2026-09-18）

### 0. 为什么要做这个实验

`multi_hop` 是五类指标里最弱的一类（accuracy **0.20**，5 题里只有 1 题完全正确），
而项目当时**缺一个"前后对比"的数字**。

### 1. 方法學前提（**先写清楚，否则实验必然自欺**）

1. **样本量极小**：只有 **5 道**多跳题 → 1 题翻转就是 `0.20 → 0.40`。
   **这个样本量做不了统计推断**，任何"提升"都只能算**方向性证据**。
2. **所以主指标不用准确率**，改用检索层的可诊断指标：
   > **`gold_sources` 的全部依据是否都进了候选池 / top-k？**
3. 为什么需要这个新指标 —— **现有 `hit_rate` 有一个盲区**：
   `eval/metrics.py` 的 `hit_at_k` 是「**任一** `gold_source` 命中即算命中」，
   所以多跳题报的 `hit 5/5` **只说明两篇依据里找到了至少一篇**，并不代表两篇都进了 top-k。
   而且 `hit_at_k` **对 k 单调**（k 越大越容易命中），因此 **`hit_rate` 不能用来跨 k 比较质量** —— 这一条是本实验的副产品发现。

### 2. 受控条件

| 项 | 状态 |
|---|---|
| 题库 | `eval/questions.jsonl` **冻结，一字未改**（20 题：单跳 12 / 多跳 5 / 不可答 3） |
| 语料 | `data/raw/` 12 份 / 400 块，**冻结** |
| 生成模型 | DeepSeek `deepseek-chat`，`temperature=0` |
| 向量模型 | 百炼 `text-embedding-v3`（1024 维） |
| **唯一自变量** | **`TOP_K_FINAL`**（环境变量，改它不需要动代码） |

### 3. Step 0 · 诊断（只调 query embedding，不调生成）

对 5 道多跳题，统计两篇依据各进了几篇（原始输出，`fused` = 融合池，`final` = 最终 top-4）：

| 题 | 判分 | fused 覆盖 | final(top-4) 覆盖 | final 里出现的来源 |
|---|---|---|---|---|
| `q13` | **wrong** | 2/2 | **1/2** | `02_Vue3_响应式基础.md`, `05_Vue3_组合式函数.md` |
| `q14` | partial | 2/2 | 2/2 | `02_…`, `04_Vue3_计算属性.md`, `05_…` |
| `q15` | correct | 3/3 | **2/3** | `08_FastAPI_查询参数.md`, `09_FastAPI_请求体.md` |
| `q16` | partial | 2/2 | 2/2 | `01_Vue3_快速上手.md`, `03_Vue3_组件基础.md` |
| `q17` | partial | 2/2 | 2/2 | `02_…`, `03_…`, `04_…`, `05_…` |

**汇总**：
- 融合池里两篇（及以上）依据**全部覆盖 = 5/5**
- 最终 top-4 里全部覆盖 = **3/5**（`q13`、`q15` 各被截断掉一篇）

**对照**：`single_hop` 的唯一依据进 top-4 = **11/12**（未命中只有 `q07`）。

**诊断结论**：召回没问题（候选池里**永远**能找到全部依据）；`top-4` 截断会丢依据，但只影响 5 题里的 2 题。

### 4. Step 1 · 变体对照（`TOP_K_FINAL` 4 → 8）

同一套题、同一份语料、同一模型、同一天，只改这一个环境变量：

| 指标 | V1 基线（`top_k=4`） | V2（`top_k=8`） | 差异 |
|---|---|---|---|
| `accuracy` | 0.50 | 0.55 | +0.05（= **1 题**） |
| `partial_rate` | 0.25 | 0.30 | +0.05 |
| `wrong_rate` | 0.25 | 0.15 | −0.10（= 2 题） |
| `refusal_accuracy` | 1.00 | 1.00 | 0 |
| `hit_rate` | 0.80 | 0.85 | +0.05（**注意：对 k 单调，不可比**） |
| `avg_latency_ms` | 1316.3 | 1300.8 | −15.5（基本不变） |
| **`single_hop` 对/部分/错** | 6 / 2 / 4 | 7 / 3 / 2 | +1 题 |
| **`multi_hop` 对/部分/错** | **1 / 3 / 1** | **1 / 3 / 1** | **0（一分未动）** |
| `unanswerable` 对/部分/错 | 3 / 0 / 0 | 3 / 0 / 0 | 0 |
| 主指标：多跳「依据全进 top-k」 | 3/5 | 4/5 | +1 题（截断确实缓解了） |

原始产出文件：`eval/report.json`（V1，官方基线）、`eval/report_v2_topk8.json`（V2）；
逐题明细：`eval/report_detail.json`、`eval/report_detail_v2_topk8.json`（均在本地，被 `.gitignore` 挡住）。

### 5. 结论

1. **多跳题的瓶颈不是检索召回。** 决定性证据：把候选从 4 扩到 8，**`multi_hop` 一分未动（仍是 1/5）**；
   而融合池里两篇依据**本来就 5/5 全覆盖**。所以"扩大召回范围"这条路对多跳题无效。
2. **瓶颈在生成侧的跨文档综合。** `q14`/`q16`/`q17` 两篇依据**都在 top-4 里**，却只拿到"部分对" —— 说明资料给到了，模型没综合好。
3. **V2 的总体提升不构成"更好"的证据。** `accuracy 0.50 → 0.55` 与 `single_hop 6 → 7` 都只是 **1 题**的差别；
   项目已记录的运行间波动区间是 **0.45–0.50（±1 题量级）**（`PLAN.md §5.5`），因此这个差异**无法与噪声区分**。
4. **`hit_rate 0.80 → 0.85` 不能当作质量提升**：`hit_at_k` 对 k 单调，k 变大命中率机械上升。
5. **因此不建议改 `TOP_K_FINAL` 的默认值**（`SPEC.md §5` 定为 4）。没有证据表明 8 更好，而改默认值需要先改契约、另开卡。
6. **V3（父子分块 / 按来源限流）本次不做**：它们的动机是"召回不够"，而诊断显示召回**已经足够**。
   若将来要做父子分块，应当把它设计成**生成侧改进**（给综合提供更完整的上下文），而不是检索侧改进 —— 这个动机上的区分比改动本身更重要。

### 6. 方法学限制（**必须与结论一起引用**）

- **5 道多跳题做不了统计推断**：本实验只能给出方向性判断，不能给出"提升 X 个百分点"的结论。
- **准确率有运行间波动**：同输入连跑三次实测 0.45 / 0.45 / 0.50（`PLAN.md §5.5`）。
- **`hit_rate` 跨 k 不可比**（单调性，见上）。
- **向量检索层本身不可跨进程复现**（`PLAN.md §5.12`）：逐次召回的 chunk 排名并非完全一致，
  本实验的"两篇依据是否都进 top-k"是**集合级**判断，因此比逐条排名稳定，但仍带这一层不确定性。
- 本实验**没有**做多轮重复（每个变体只跑一次）—— 因为每次都是一次真实 API 评测（有成本），
  且单轮就足以否证"扩大召回能救多跳题"这一假设。
