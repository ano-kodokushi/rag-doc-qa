# 对照实验记录（EXPERIMENTS）

本文件存放**受控对照实验**的设计、原始数据与结论。
每条实验都必须写明：受控条件、自变量、**方法学限制**、以及结论是「方向性证据」还是「统计显著」。

**为什么单独建这个文件**：项目的评测数字（`eval/report.json`）只说"现在是多少"，
而对照实验回答的是"**改动到底有没有用**"。这两件事必须分开存放，否则很容易把波动当成进步。

## E-01 · multi-hop 的瓶颈在检索还是生成？（T-016，2026-09-18）

### 0. 为什么要做这个实验

`multi_hop` 是五类指标里最弱的一类（accuracy **0.20**，5 题里只有 1 题完全正确），
而项目当时**缺一个"前后对比"的数字**。

### 1. 方法學前提（**先写清楚，否则实验必然自欺**）

1. **样本量极小**：只有 **5 道**多跳题 → 1 题翻转就是 `0.20 → 0.40`。
   **这个样本量做不了统计推断**，任何"提升"都只能算**方向性证据**。
2. **所以主指标不用准确率**，改用检索层的可诊断指标：
   > **`gold_sources` 的全部依据是否都进了候选池 / top-k？**
3. 为什么需要这个新指标 —— **现有 `hit_rate` 有一个盲区**：
   `eval/metrics.py` 的 `hit_at_k` 是「**任一** `gold_source` 命中即算命中」，
   所以多跳题报的 `hit 5/5` **只说明两篇依据里找到了至少一篇**，并不代表两篇都进了 top-k。
   而且 `hit_at_k` **对 k 单调**（k 越大越容易命中），因此 **`hit_rate` 不能用来跨 k 比较质量** —— 这一条是本实验的副产品发现。

### 2. 受控条件

| 项 | 状态 |
|---|---|
| 题库 | `eval/questions.jsonl` **冻结，一字未改**（20 题：单跳 12 / 多跳 5 / 不可答 3） |
| 语料 | `data/raw/` 12 份 / 400 块，**冻结** |
| 生成模型 | DeepSeek `deepseek-chat`，`temperature=0` |
| 向量模型 | 百炼 `text-embedding-v3`（1024 维） |
| **唯一自变量** | **`TOP_K_FINAL`**（环境变量，改它不需要动代码） |

### 3. Step 0 · 诊断（只调 query embedding，不调生成）

对 5 道多跳题，统计两篇依据各进了几篇（原始输出，`fused` = 融合池，`final` = 最终 top-4）：

| 题 | 判分 | fused 覆盖 | final(top-4) 覆盖 | final 里出现的来源 |
|---|---|---|---|---|
| `q13` | **wrong** | 2/2 | **1/2** | `02_Vue3_响应式基础.md`, `05_Vue3_组合式函数.md` |
| `q14` | partial | 2/2 | 2/2 | `02_…`, `04_Vue3_计算属性.md`, `05_…` |
| `q15` | correct | 3/3 | **2/3** | `08_FastAPI_查询参数.md`, `09_FastAPI_请求体.md` |
| `q16` | partial | 2/2 | 2/2 | `01_Vue3_快速上手.md`, `03_Vue3_组件基础.md` |
| `q17` | partial | 2/2 | 2/2 | `02_…`, `03_…`, `04_…`, `05_…` |

**汇总**：
- 融合池里两篇（及以上）依据**全部覆盖 = 5/5**
- 最终 top-4 里全部覆盖 = **3/5**（`q13`、`q15` 各被截断掉一篇）

**对照**：`single_hop` 的唯一依据进 top-4 = **11/12**（未命中只有 `q07`）。

**诊断结论**：召回没问题（候选池里**永远**能找到全部依据）；`top-4` 截断会丢依据，但只影响 5 题里的 2 题。

### 4. Step 1 · 变体对照（`TOP_K_FINAL` 4 → 8）

同一套题、同一份语料、同一模型、同一天，只改这一个环境变量：

| 指标 | V1 基线（`top_k=4`） | V2（`top_k=8`） | 差异 |
|---|---|---|---|
| `accuracy` | 0.50 | 0.55 | +0.05（= **1 题**） |
| `partial_rate` | 0.25 | 0.30 | +0.05 |
| `wrong_rate` | 0.25 | 0.15 | −0.10（= 2 题） |
| `refusal_accuracy` | 1.00 | 1.00 | 0 |
| `hit_rate` | 0.80 | 0.85 | +0.05（**注意：对 k 单调，不可比**） |
| `avg_latency_ms` | 1316.3 | 1300.8 | −15.5（基本不变） |
| **`single_hop` 对/部分/错** | 6 / 2 / 4 | 7 / 3 / 2 | +1 题 |
| **`multi_hop` 对/部分/错** | **1 / 3 / 1** | **1 / 3 / 1** | **0（一分未动）** |
| `unanswerable` 对/部分/错 | 3 / 0 / 0 | 3 / 0 / 0 | 0 |
| 主指标：多跳「依据全进 top-k」 | 3/5 | 4/5 | +1 题（截断确实缓解了） |

原始产出文件：`eval/report.json`（V1，官方基线）、`eval/report_v2_topk8.json`（V2）；
逐题明细：`eval/report_detail.json`、`eval/report_detail_v2_topk8.json`（均在本地，被 `.gitignore` 挡住）。

### 5. 结论

> ⚠️ **本节第 1、2、6 条已被 `E-02` 推翻**（连续覆盖率显示：扩大召回**真实有效**，只是没跨过判分阈值；
> 瓶颈在**小节级检索精度**，而不是生成侧）。**保留原文以便对照，一律以 `E-02` 为准。**

1. **多跳题的瓶颈不是检索召回。** 决定性证据：把候选从 4 扩到 8，**`multi_hop` 一分未动（仍是 1/5）**；
   而融合池里两篇依据**本来就 5/5 全覆盖**。所以"扩大召回范围"这条路对多跳题无效。
2. **瓶颈在生成侧的跨文档综合。** `q14`/`q16`/`q17` 两篇依据**都在 top-4 里**，却只拿到"部分对" —— 说明资料给到了，模型没综合好。
3. **V2 的总体提升不构成"更好"的证据。** `accuracy 0.50 → 0.55` 与 `single_hop 6 → 7` 都只是 **1 题**的差别；
   项目已记录的运行间波动区间是 **0.45–0.50（±1 题量级）**（`PLAN.md §5.5`），因此这个差异**无法与噪声区分**。
4. **`hit_rate 0.80 → 0.85` 不能当作质量提升**：`hit_at_k` 对 k 单调，k 变大命中率机械上升。
5. **因此不建议改 `TOP_K_FINAL` 的默认值**（`SPEC.md §5` 定为 4）。没有证据表明 8 更好，而改默认值需要先改契约、另开卡。
6. **V3（父子分块 / 按来源限流）本次不做**：它们的动机是"召回不够"，而诊断显示召回**已经足够**。
   若将来要做父子分块，应当把它设计成**生成侧改进**（给综合提供更完整的上下文），而不是检索侧改进 —— 这个动机上的区分比改动本身更重要。

### 6. 方法学限制（**必须与结论一起引用**）

- **5 道多跳题做不了统计推断**：本实验只能给出方向性判断，不能给出"提升 X 个百分点"的结论。
- **准确率有运行间波动**：同输入连跑三次实测 0.45 / 0.45 / 0.50（`PLAN.md §5.5`）。
- **`hit_rate` 跨 k 不可比**（单调性，见上）。
- **向量检索层本身不可跨进程复现**（`PLAN.md §5.12`）：逐次召回的 chunk 排名并非完全一致，
  本实验的"两篇依据是否都进 top-k"是**集合级**判断，因此比逐条排名稳定，但仍带这一层不确定性。
- 本实验**没有**做多轮重复（每个变体只跑一次）—— 因为每次都是一次真实 API 评测（有成本），
  且单轮就足以否证"扩大召回能救多跳题"这一假设。

## E-02 · 重读 E-01：连续覆盖率**推翻**了 E-01 的结论（T-018，2026-09-18）

> ⚠️ **E-01 的第 5 节结论「检索侧无效、瓶颈在生成侧」是错的。本节是更正，以本节为准。**

### 1. 为什么要重读

E-01 用**判分桶**（对 / 部分对 / 错，阈值 = keypoint 覆盖率 ≥ 0.8）比较 V1/V2，于是 5 道多跳题只要没有整题翻转，看起来就是"一分未动"。
但 `keypoints_match` 本身返回 **0~1 的连续值**，桶把中间信息全丢了。
用连续值重读**同一批已有数据**（零成本，只读 `eval/report_detail*.json`）：

| 指标 | V1（`top_k=4`） | V2（`top_k=8`） | 变化 |
|---|---|---|---|
| `single_hop` 平均 keypoint 覆盖率 | 0.569 | **0.667** | +0.098 |
| `multi_hop` 平均 keypoint 覆盖率 | 0.450 | **0.550** | +0.100 |
| 逐题覆盖率升降 | — | — | **上升 5 题 / 下降 0 题 / 持平 12 题** |

上升的 5 题：`q03` 0.00→0.33、`q07` 0.00→0.33、`q11` 0.50→1.00、`q14` 0.25→0.50、`q16` 0.50→0.75。

**单调向上、零下降** —— 在"抛硬币"零假设下 **p ≈ 0.031（单侧符号检验，5 升 0 降）**。
这是本项目目前**最强的统计证据**。

**所以正确的表述是**：不是"扩大召回无效"，而是「**扩大召回有真实效果，但不足以跨过 0.8 的桶阈值，于是桶看不见**」。

### 2. 真正的瓶颈在哪一层（三层都试过）

| 曾怀疑的瓶颈 | 证据 | 判决 |
|---|---|---|
| 文件级召回 | 融合池 **5/5** 覆盖全部 `gold` 文件 | ❌ 不是 |
| 生成侧跨文档综合 | 模型答"资料里没有" —— 而内容**确实不在它看到的小节里** | ❌ **不是（E-01 说错了）** |
| **小节级检索精度** | 上升的 5 题全是"多给几块后**对的小节**进来了"；下面 6 题缺的内容**全在语料里**，只是检索到同一文件的**错误小节** | ✅ **是这里** |

逐题证据（取自 `eval/report_detail.json` 里模型的真实回答）：

| 题 | 模型的回答 | 语料里的真相 |
|---|---|---|
| `q03` | 「根据现有资料**无法回答**」 | `02_Vue3_响应式基础.md` 有 `### reactive() 的局限性`，**三个局限一字不差** |
| `q12` | 「资料**没有说明**哪两种情况必须写 `.value`」 | 同文件有 `### 数组和集合的注意事项` + `### 在模板中解包的注意事项` |
| `q13` | 「资料中**没有直接给出**官方推荐倾向」 | 原文：`由于这些限制，我们建议使用 ref() 作为声明响应式状态的主要 API` |
| `q14` | 「资料**没有对**计算属性与普通函数调用**进行对比**」 | `04_Vue3_计算属性.md` 有整节 `## 计算属性缓存 vs 方法` |
| `q16` | 「不使用构建步骤时**资料中未展开说明**」 | `03_Vue3_组件基础.md` 原文：`以一个包含 Vue 特定选项的 JavaScript 对象来定义`、`Vue 将会在运行时编译它` |
| `q17` | 「资料**没有包含**组件间传递数据这部分」 | 同文件有 `## 传递 props` + `## 监听事件` |

> **模型的回答是诚实的**：它每次说"资料里没有"，而检索给它的上下文里**确实没有**。
> 所以这既不是幻觉、也不是生成能力问题，而是**给错了小节**。

### 3. 方法学教训（**本项目最重要的一条**）

**粒度决定了你能看见什么。** 同一批数据，三层指标给出三个互相矛盾的结论：

| 指标粒度 | 它说的话 | 真相 |
|---|---|---|
| 文件级（`hit_at_k`） | "召回没问题"（且它**对 k 单调**、还是"**任一**命中即算"） | 粗了两层 |
| 桶级（阈值 0.8） | "检索侧无效" | 粗了一层 |
| **连续覆盖率** | **"有效，只是不够跨阈值"** | ✅ |

推论：
1. 比较任何检索/生成改动时，**主指标用连续 keypoint 覆盖率**，桶指标只作参考。
2. `hit_rate` **不能跨 k 比较**（单调性，见 E-01）。
3. **`keypoints_match` 是字面子串匹配** —— 改写措辞即判错（例：`q02` 模型说"原始值 / 对象"，
   而 keypoints 是"原始类型 / 对象类型"）。**所有准确率数字都必须带这条限制引用**；
   若将来要改（语义判分 / 同义词表），属单独一张卡，且会**破坏与历史数字的可比性**。

### 4. 还有 4 题连 `top_k=8` 都没救

`q02` / `q12` / `q13` / `q17` 的覆盖率在 V2 下**仍未上升**。
→ 光加 k 不够，需要**把命中块所在的小节一起给模型**（父子分块的最小形态），而不是继续加大 k。

### 5. 对后续实验的约束（写进规范）

- 主指标：**逐题连续 keypoint 覆盖率** + 升降计数；桶指标（对/部分对/错）仅作汇报用。
- 每次对照必须报：受控条件、逐题覆盖率、升降计数、**样本量限制**（多跳题只有 5 道）。
- **负结果与正结果同等对待**：E-01 的结论被 E-02 推翻，本身说明"记录 + 可重读的原始数据"比结论更重要 ——
  这也是为什么每个实验都必须把**原始产出文件**（`eval/report*.json`）留在本地。

## E-03 · 小节级整理三模式对照：`diverse` 更差、`expand` 持平但大面积丢资料（T-020，2026-09-21）

### 0. 假设与来源

E-02 定位到「检索到同一文件的**错误小节**」。据此设计三个模式（**唯一自变量 `SECTION_MODE`**）：

| 值 | 行为 |
|---|---|
| `off` | 现状：top-k 的块原样返回 |
| `diverse` | 按 `(source, heading)` 去重，每节保留排名最高的一块，**文本不扩展** |
| `expand` | 去重 + 文本换成**该小节全文** |

**预期**：既然需要的内容常在同一文档的**另一个小节**，`diverse`（用同样的 k 覆盖更多小节）应当最好。

### 1. 受控条件

题库 / 语料 / 模型 / `top_k_final=4` 全部冻结，**唯一自变量 `SECTION_MODE`**；每个模式一次真实评测（合计约 0.3 元）。
原始产出：`eval/report_t020_{off,diverse,expand}.json` 与对应 `report_detail_t020_*.json`（本地，已 gitignore）。
prompt 长度那两行不在这些文件里，来自另一次**只跑检索**的复算，口径见 §2 表格下方的说明。

### 2. 结果

| 指标 | `off`（基线） | `diverse` | `expand` |
|---|---|---|---|
| **`avg_keypoint_coverage`** | **0.5343** | 0.5147（↓） | **0.5441**（↑ 但在噪声内） |
| `accuracy` | 0.50 | 0.45 | 0.50 |
| `partial_rate` / `wrong_rate` | 0.25 / 0.25 | 0.35 / 0.20 | 0.25 / 0.25 |
| `refusal_accuracy` / `hit_rate` | 1.00 / 0.80 | 1.00 / 0.80 | 1.00 / 0.80 |
| `avg_latency_ms` | 1235.5 | 1147.4 | 1244.0 |
| prompt 中位 / 最大 | 1624 / 1936 | 1465 / 1936 | **2388 / 4742** |
| **有资料被丢掉的题数** | **0** | **0** | **14**（`q01`/`q03`/`q04`/`q05`/`q06`/`q07`/`q08`/`q09`/`q11`/`q12`/`q13`/`q14`/`q16`/`q17`） |
| 其中"最终 prompt 仍超 3000"的题 | 0 | 0 | **4**（`q04`/`q07`/`q11`/`q14`） |
| 逐题覆盖率升降 | — | 升 1 / 降 1 | 升 2 / 降 1 |

逐题明细：
- `diverse`：`q02` 0.00→0.33；**`q04` 1.00→0.33**（净负）
- `expand`：`q02` 0.00→0.67、`q16` 0.50→1.00；**`q04` 1.00→0.00**（被截断所致）

> **prompt 长度与"丢资料"的行是怎么来的（口径必须写清楚）**：这几行**不是**那三次评测的产物 ——
> 逐题明细文件里没有 prompt 长度字段。它们来自一次**只跑检索、不调用 LLM**的本地复算
> （`Retriever.search()` + `build_prompt(max_chars=3000)`，成本只有 60 次 query embedding，约 0 元）。
> 「有资料被丢掉」的判据是 `len(build_prompt(..., 3000)) < len(build_prompt(..., 0))`，即**有限预算下被 break 掉的资料数 > 0**；
> 而「最终 prompt 仍超 3000」是更窄的判据（连第 1 条资料都塞不进预算）。
> **两个数都是真的，但用哪个口径会决定你看见什么** —— 这正是 E-02 的教训在这里重演一次。

### 3. 结论（**假设被证伪：两个模式都没有净收益**）

1. **`diverse` 比基线更差**（覆盖率 −0.020、accuracy −0.05）：去重**减少了进入上下文的块数**（材料从 4 条降到 2~4 条），
   换来的"小节多样性"补不回丢掉的内容。
   → **"用同样的 k 覆盖更多小节"这个想法不成立**：**内容总量**比小节多样性更重要。
2. **`expand` 覆盖率 +0.010，但落在噪声内**（逐题 升 2 / 降 1），代价却是**大面积丢资料**：
   **14 / 20 题**有资料被 3000 字符预算 break 掉，其中 **4 题**（`q04`/`q07`/`q11`/`q14`）连第 1 条都塞不进、最终 prompt 仍超 3000，
   而 `q04` 直接从 1.00 掉到 0.00。
   **还有一类更隐蔽的破坏**：`build_prompt` 是"遇到第一条塞不下就 `break`"，
   所以当**第 2 条小节特别长**时，模型最后只拿到第 1 条**很小**的材料 —— `q05` 只剩 **346 字符**、`q09` 只剩 **200 字符**、`q08` 只剩 **560 字符**
   （它们的完整材料分别是 6128 / 4558 / 4585 字符）。**prompt 变短不一定是好事，这里是把上下文掏空了。**
   → **收益不显著、风险明确且量级很大**，不能作为默认值。
3. **因此 `SECTION_MODE` 的默认保持 `off`**；代码与测试保留，作为**可复现的实验装置**。
4. **与 E-02 合起来看，故事是一致的**：

   | 改动 | 方向 | 覆盖率结果 |
   |---|---|---|
   | `top_k` 4→8（E-02） | **内容更多** | **5 升 0 降**（有效） |
   | `diverse`（E-03） | **内容更少** | 更差 |
   | `expand`（E-03） | **内容更长但被截断** | 持平偏险 |

   → **真正起作用的是「上下文里有没有那段内容」，而不是它怎么排列、怎么拼长。**
5. **矛头指向「排序」**：需要的内容**明明在融合池里**（E-01 已证：文件级 5/5），却没进 top-k 的窗口 ——
   这正是 **rerank** 要解决的问题。而 `src/retrieve.py` 里的 rerank **已实现、`RERANK_ENABLED=0` 从未启用、也从未用真实 API 验证过**。

### 4. 方法学限制

- 每题只跑一次；n=20，且只有 2~3 题发生移动 → **不能做统计推断**。
  （E-02 的"5 升 0 降"是特例的强信号，本实验没有这种信号 —— **不要把 ±0.01 的覆盖率差异当成改善**。）
- 三个模式的 `hit_rate` 都是 0.80 → 检索层稳定，差异来自生成侧看到的上下文。
- **`expand` 的大面积丢资料是本实验最大的混杂因素**：它的覆盖率数字**严重低估**了"无截断时的扩展效果"。
  要公平评估就得提高 `max_chars`（`SPEC.md §5` 的默认 3000）—— 那属于另一张卡。
  也可以说：**`expand` 的失败至少有一半是预算问题，不全是"整理方式"的问题** —— 这条要说在结论里，不能含糊过去。
- 同一份代码**跨进程复算** prompt 长度时，`vector` 层会漂移（§5.12），所以上表的 prompt 数字应读作**量级**，
  不要当成逐字常量；但"`expand` 会让十几道题丢资料"这个结论对漂移不敏感（它由小节字数决定）。

## E-04 · rerank 真实验证：总覆盖率 0.549 → 0.637，**但多跳题零效果**，代价是每次 +2.0 s（T-021，2026-09-21）

> **这是本项目第一个正面结果**（E-01 被推翻、E-02 是更正、E-03 是负结果，都只到"排除了什么"）。
> 但它**不改变默认值** —— 理由见 §5。

### 0. 假设与来源

E-01/E-02/E-03 三个实验把矛头收敛到**排序**：
内容**已经在融合池里**（文件级 5/5）、扩大窗口**有效**（`top_k` 4→8 覆盖率 5 升 0 降）、
而"整理材料的方式"**无效**（`diverse` 更差、`expand` 持平偏险）。
⇒ 缺的不是内容、也不是排列，而是**排序精度**：该进 top-k 的块没进来。

`src/retrieve.py:203-288` 的 rerank 正是为此写的，但 `RERANK_ENABLED=0`、**从未启用、从未联网验证**。

### 3. 受控条件（这次为什么不是"跑两个进程"）

`PLAN.md §5.12` 已证 **chroma 的向量层不可跨进程复现**。若用两条 `python -m eval.run_eval` 做 A/B，

- **同一个 `Retriever` 实例**（同一份 BM25 缓存、同一份 `chunk_map`、同一个 chroma 句柄）
- 只用 `search(..., use_rerank=...)` 这一个参数切换，包一个只注入该参数的薄代理交给 `run_once`
- ⇒ 除 rerank 本身外，两条路径**共享同一份检索状态**

题库 / 语料 / 生成模型 / `top_k_final=4` / `SECTION_MODE=off` 全部冻结。**唯一自变量 `use_rerank`**。
原始产出：`eval/report_t021_rerank_{off,on}.json` 与 `report_detail_t021_rerank_{off,on}.json`（本地，已 gitignore）。

这条必须紧挨着结论的第一句，否则会得出「排序就是多跳瓶颈、rerank 已经解决它」这个**错误**结论 ——
而本实验的动机恰恰是**多跳**。真实情况是：**排序确实是全库的瓶颈之一（单跳有效），但它不是多跳的瓶颈。**
一个可解释的机制（**只是假设，本实验没有设计能证伪它的对照**）：
rerank 按「**单个 query 的相关性**」打分，而多跳题需要的是**跨两篇文档的互补覆盖** ——
它会把"第二跳"那篇挤出去，`q14` 正是这个表现。

**三条"确实生效"的证据（缺一条都不能说 rerank 起作用了）**
1. **`_rerank` 被调用 20 次、异常 0 次**（脚本内探针计数）→ 不是"静默降级后看起来没效果"
2. **20 / 20 题的 top-k 顺序被改变** → 输出确实经过重排
3. **"rerank 输出的 chunk 全部来自融合池"被违反 0 题** → 重排没有偷换候选集（它只能在池子里换顺序，符合设计）

### 5. 结论

0. ⚠️ **先说最重要的一条（否则下面的数字会被误读）：rerank 对多跳题「零效果」。**
   收益**全部**来自单跳题（`single_hop` 覆盖率 0.5694 → 0.6944，桶内 5/4/3 → 6/5/1）；
   多跳题覆盖率均值 **0.5000 → 0.5000**、桶内 **1/3/1 → 1/3/1**，两题一升一降精确抵消。
   **本实验的动机是修多跳，而多跳没被修好。** 详见 §4 的按题型拆解。
1. **但 rerank 在本语料与题库上确实有效**：主指标 **+0.088**（0.549 → 0.637），逐题 **升 4 / 降 1**、
   `wrong_rate` **0.20 → 0.10（腰斩）** —— 幅度远超 `§5.5` 记录的运行间波动（覆盖率 ±0.01~0.02）。
   即：**排序是全库的瓶颈之一，但不是多跳的瓶颈。** 这两句话必须一起说。
2. **代价是延迟**：单题 **+2.05 s**（1136 → 3188 ms，+1.8 倍），因为每次都多一次跨网调用
3. **因此本卡不改默认值**：`RERANK_ENABLED` 仍为 `0`。理由是**收益与成本要由使用方按场景权衡**
   （离线批量评测偏质量、在线问答偏延迟），而且 `SPEC.md` 把 rerank 列为**二期可选** ——
   改默认值是另一张卡 + 用户批准的事（详见 `BOARD.md` 决策日志）
4. **对前面实验的收口（但只收到一半）**：E-01/E-02/E-03 把矛头指向"排序"，本实验给出**部分确认** ——
   同一份融合池、只换顺序，主指标就涨了 0.088，**说明"排序"这条线本身是通的**；
   但**它并没有回答"多跳为什么差"**，因为多跳那一栏纹丝不动。
   证据链现在的状态：**内容在池子里（E-01）→ 扩大窗口对多跳有效（E-02）→ 排列方式无效（E-03）→ 排序对单跳有效、对多跳无效（E-04）**
   ⇒ **多跳的瓶颈仍然未知**，已知的排除项是：文件级召回、窗口大小（部分）、材料排列、以及现在的"全局重排"
5. **下一步的候选（都未开卡，按证据强度排序）**：
   - **`top_k` 与 rerank 联合调参**：E-02 说"窗口更大 → 多跳更好"，E-04 说"重排 → 多跳无效"。
     两者合起来暗示一个**可证伪**的假设：**先扩大窗口再多给几条（例如 `RERANK_ENABLED=1` 且 `top_k_final=8`）**，
     让 rerank 只做"排序"而**不替多跳题做"取舍"**。这是最便宜、最直接的下一个实验
   - **保证跨文档覆盖的排序**：例如按 `source` 限制每条来源最多占几个席位（E-01 提出的"多路召回"），
     这与 rerank 的"单 query 相关性"是正交的，恰好能补上它挤掉第二跳的倾向

### 7. 方法学限制

- **每题只跑一次，n=20，5 题发生移动** → 与 E-02 同量级的信号强度，但**仍不是统计检验**；
  引用时说"单次运行、逐题升 4 降 1"，不要说"提升 8.8 个百分点"这种精确口径
- ⚠️ **最重要的一条：总体数字会掩盖"分题型后结论完全不同"**。
  只看总覆盖率是 **+0.088（有效）**，按题型拆开是 **单跳 +0.125 / 多跳 ±0.000（零效果）**。
  而本实验的动机是**多跳** —— **如果只报总体数字，就等于用一个"看起来成功"的结论掩盖了"目标没达成"**。
  这是 E-02「粒度决定你能看见什么」的**第三次**重演（第一次是文件级/桶级/连续值，第二次是"截断"的两种口径）
- **`q14` 是唯一变差的题**（0.500 → 0.250）：说明 rerank **不是单调改进**，
  它会把某些题的正确答案排下去。**这一条必须主动说**，否则等于只报好看的一半
- **rerank 分数的绝对大小无意义**：官方文档明确"此分数为当前请求内的相对分数，**不可跨请求比较**"。
  我们的实现只在**一次请求内**排序，正好符合这个约束 —— 但**不要**把 `relevance_score` 当成可跨题比较的质量分
- **同进程设计是优点也是边界**：它排除了向量漂移这个混杂因素，但代价是
  **本实验的数字不能直接和 `report.json` 的历史数字比**（那次是另一个进程、另一次召回）。
  基线 `0.5490` 与 T-020 的 `0.5343` 的差异来自 LLM 波动与召回漂移，**不是**"改了什么东西"
- **延迟数字含网络抖动**：`+2.05 s` 是一次 20 题运行的均值，未做多次重复取中位；量级可信、小数点不可信
- **P2 的"qwen3-rerank 兼容嵌套 body"是实测行为、不是文档承诺**：官方文档说的是扁平形状。
  若哪天老端点下线或去掉兼容层，`RERANK_MODEL=qwen3-rerank` 会开始抛异常 → 被降级吞掉 →

## E-05 · `top_k` × rerank 联合：H1 被证伪，**0 元的机制诊断省下了 0.9 元**（T-022，2026-09-21）

### 0. 假设与来源

E-02 与 E-04 的交叉点：
- E-02：`top_k` 4→8 → 多跳覆盖率 **0.450 → 0.550（5 升 0 降）** ⇒ **扩大窗口对多跳有效**
- E-04：rerank 开着、窗口仍 4 → 多跳覆盖率 **0.500 → 0.500（±0.000）** ⇒ **重排对多跳无效**

**H1（可证伪）**：rerank 对多跳无效，是因为窗口只有 4 个席位、它在**替多跳题做取舍**（把"第二跳"挤出去，`q14` 正是这个表现）。
⇒ 预测：**先把窗口扩到 8 再重排，被挤掉的依据应当回来**，即 `(k=8, on)` 的多跳"两篇依据都进窗口"应 ≥ `(k=8, off)`。

**T-022 的设计：先花 0 元看机制，再决定要不要花 0.9 元。** 机制诊断只看**窗口里有没有那篇依据**，不需要任何 LLM 调用。

### 1. Step 1 · 检索侧机制诊断（**无任何 LLM/生成调用**；80 次 query embedding + 40 次 rerank 调用，约 0.01 元）

> ⚠️ **每行分母不同，必须看清**（独立验证抓到过这里的一处口径错误，见 §7）：
> - 「平均命中依据篇数」**分母 = 20 题**（3 道不可答题 `gold_sources` 为空，天然贡献 0 篇）
> - 「全部依据都进窗口」**分母 = 有依据的 17 题**（不可答题的"全部依据"是空集，计入等于白送 ✅，故**不计**）
> - 多跳 / 单跳两列的分母分别是 **5 题 / 12 题**

| 配置 | 平均命中依据篇数<br>（/20） | **有依据的 17 题中「全部依据都进窗口」**<br>（/17） | **多跳两篇都进窗口**<br>（/5） | 单跳依据进窗口<br>（/12） |
|---|---|---|---|---|
| `k=4, off` | 1.000 | 14 / 17 | **3 / 5** | 11 / 12 |
| `k=8, off` | **1.100** | **16 / 17** | **4 / 5** | **12 / 12** |
| `k=4, on` | 1.000 | 14 / 17 | **2 / 5** | 12 / 12 |
| **`k=8, on`（H1 的关键格）** | 1.050 | 15 / 17 | **3 / 5** | 12 / 12 |

> 若把分母统一成 20 题（不可答题按"空集全部进窗口"计 ✅），同一行是 **17 / 19 / 17 / 18**；
> 两个数都对，只是分母不同 —— **写清分母比写哪一个数更重要**。

**H1 的预测是 `(k=8,on)` ≥ `(k=8,off)`；实测 `3/5 < 4/5`。⇒ H1 被证伪。**

**多跳题的文件级连续覆盖率**（= 进窗口的 gold 篇数 / gold 总篇数，作为 §2.12 预注册判据的代理指标）：
`k=4,off` **0.8333** · `k=8,off` **0.9000** · `k=4,on` **0.7333** · **`k=8,on` 0.8333**
→ 同样满足 `(k=8,on) < (k=8,off)`，**换口径后方向不变**（这正是"不靠挑指标得结论"的检验）。

### 2. 三条"rerank 真的在跑"的证据（照用 E-04 的方法，缺一条都不能下结论）

1. **`_rerank` 被调用 40 次 / 异常 0 次**（预期 = 20 题 × 2 个 `on` 配置）
2. **`(k,off)` 与 `(k,on)` 的窗口"内容不同"的题数** —— **同一件事在三种粒度上给出三个不同的数**，
   所以**必须把键写死**（这是「粒度决定你能看见什么」在本项目里的**第四次**现身）：

   | 比较键 | k=4 | k=8 |
   |---|---|---|
   | **`chunk_id` 列表**（`[h.chunk_id for h in hits]`） | **20 / 20** | **20 / 20** |
   | **有序 `source` 列表**（保留重复） | **13 / 20** | **19 / 20** |
   | **`source` 去重集合**（`set(...)`） | **10 / 20** | **12 / 20** |

   - 为什么三个数不同（**逐题核过，不是推测**）：
     - k=4 有 **3 题**（`q01`/`q12`/`q16`）是"**文件集合相同、只有顺序变了**" → 计入有序列表、不计入集合
     - 另有 **7 题**的 `source` 列表**完全相同** —— rerank **只在同一份文件内部换序**（一个窗口里往往有同一文件的多个块），
       **文件级（无论列表还是集合）都看不出**，只有 `chunk_id` 级看得出
   - ⇒ **`chunk_id` 级的 20/20 才是"rerank 确实改变了结果"的正确证据**；引用文件级数字时必须写明是列表还是集合
 
   > ⚠️ **本文档原来给的解释是错的**（独立验证第二轮抓到）：原文写"k=4 时有些题的 4 个窗口槽来自同一份文档，文件级必然相同" ——
   > 这只解释了那 7 题，却被我当成了"13 vs 20"整段差异的原因。真正的构成是 **3 题换序 + 7 题文件内换序**。
   > **错误的归因比错误的数字更难发现**（数字至少能被复算打脸），已按验证意见改写。
3. 逐题窗口内容与缺失来源**逐条打印**（见 §3），不是只报聚合数

### 3. 多跳题逐题：缺的是哪一篇

| 题 | gold 篇数 | `k=4 off` | `k=8 off` | `k=4 on` | `k=8 on` | 读法 |
|---|---|---|---|---|---|---|
| `q13` | 2 | 缺 1 | 缺 1 | 缺 1 | 缺 1 | **四种配置全缺同一篇**（`04_Vue3_计算属性.md`）→ 与窗口/重排**无关** |
| `q14` | 2 | 缺 0 | 缺 0 | **缺 1** | **缺 0** | **唯一符合 H1 的一题**：扩窗口把 rerank 挤掉的救回来了 |
| `q15` | 3 | 缺 1 | **缺 0** | 缺 1 | **缺 1** | **反例**：不开 rerank 时 8 席能装下三篇，一开 rerank 就掉一篇 |
| `q16` | 2 | 缺 0 | 缺 0 | 缺 0 | 缺 0 | 全配置都齐 |
| `q17` | 2 | 缺 0 | 缺 0 | 缺 0 | 缺 0 | 全配置都齐 |

**⇒ 结论兼有两种成分，都比"H1 成立"更有信息量：**
- **`q15` 直接证伪机制**：**8 个席位足够装下三篇依据，rerank 仍然把它们挤掉一篇** —— 所以"席位不够"不是 rerank 挤依据的原因，**是 rerank 本身的目标函数与"跨文档互补覆盖"不一致**
- **`q14` 是唯一的支持例**：扩窗口确实救回了它。**H1 不是"全错"，而是"只在个别题上成立"**
- **`q13` 与窗口/重排完全无关**：四种配置都缺同一篇 —— 这类题的问题在**融合池排名**，不在这两个旋钮上

### 4. 决策点：**不进入 Step 2（省下约 0.9 元）**

> 卡面的决策规则是"若 `(k=8,on)` 的多跳题仍然只有 1 篇依据进窗口 → H1 死，不花钱"。
> **严格说，实测的 3/5 并不是那条规则的字面触发条件**（它不是"只有 1 篇"）。
> 我按**假设本身的预测方向**判定：H1 预测 `(k=8,on) ≥ (k=8,off)`，实测**低于**，
> 而且 `q15` 给出了"席位足够仍被挤掉"的直接反例 —— 机制层面的预测已经失败，所以不再花这 0.9 元。
> **这条判定我写在这里，是为了让"我改过判据吗"这个问题有答案：判据的字面阈值我没用，我用的是更贴近 H1 的预测方向，方向是更严的（提前判定失败，而不是延后）。**

### 5. 一条顺带拿到的重要副产品（解释了 E-04 的分题型结果）

**rerank 从不通过"增加依据覆盖"来提升效果**：
- `k=4`：开 rerank 前后，平均命中依据数都是 **1.000**，可 `accuracy` 却从 0.45 升到 0.50、覆盖率 +0.088（E-04）
- `k=8`：开 rerank 反而让覆盖**变差**（1.100 → 1.050；多跳 4/5 → 3/5）

⇒ **rerank 的贡献在「把窗口内已有的块排到更前面」，而不是「把缺的块找回来」。**
这与 E-04 的分题型结论**完全自洽**：单跳题只需要"最相关那块在前面"（受益），
多跳题需要"两篇都在场"（rerank 不但帮不上，还会挤掉一篇）。

### 6. 方法学限制 / 没做的事（**必须一起引用**）

- **本实验没有 LLM 侧数据** ⇒ 「`(k=8,on)` 的**答案**是否好于 `(k=4,on)`」**仍未测**。
  我判定不必花那 0.9 元，理由是 H1 的机制预测已失败；
  但严格讲：**"机制失败"不等于"答案一定更差"**（E-04 已证 rerank 能靠排序提升单跳，而排序不体现在窗口覆盖上）。
  ⇒ **这条边界必须说清，不能说成"已证明 k=8 + rerank 没有价值"**
- **"依据进窗口"是文件级口径**：它**不能**说明"需要的那一小节"在窗口里 ——
  这正是 E-02 的结论（瓶颈在小节级精度）。所以本实验**没有**推翻 E-02，反而指向它：
  多跳题在 `k=8,off` 下已经 **4/5 文件级齐全**，答案却仍然差 ⇒ **下一个该量的是「小节级」覆盖**
- **每格只跑一次检索**：`vector` 层在同一进程内稳定，但**跨进程会漂移**（§5.12），
  所以这四格的数字只在本次进程内互相可比
- **`q13` 那种"四种配置全缺"的题**：本实验只证明它与这两个旋钮无关，**没有**定位它的原因
